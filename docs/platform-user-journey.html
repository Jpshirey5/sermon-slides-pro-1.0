Sermon Slide Pro User Journey Documentation

Prepared from the current implementation in sermon-slides-pro-1.0 as of May 17, 2026, revised August 7, 2026 for the pricing restructure (Free/Core/Team, no-payment manual builder). This is the canonical internal operations document in the /docs folder and is intended for support, onboarding, handoff, and product operations.

1. Product Summary

Sermon Slide Pro is a web application for building sermon presentations from a structured sermon form, refining them in a slide editor, and exporting them for presentation software. The application supports a free, no-account manual builder path (Try it Free, with export now free with no payment step) and authenticated subscription-based account usage (Core or Team). A separate Admin Center supports internal staff with customer, billing, support, and messaging operations.

Primary user outcome How the platform supports it
Create sermon slides quickly Structured creation flow with title, series, presentation date, points, verses, and automatic scripture lookup
Refine the sermon outline before slides are generated Sermon Review step with drag-to-reorder blocks, edits, and autosave
Refine the final deck Slide editor with generation, manual editing, reordering, background control, preview, print, and autosave
Use slides in service software Export to .pptx and .probundle, plus a Print action
Support recurring weekly workflow Saved presentations, dashboard management, account settings, subscription controls, and team support
Quantify ongoing value to the customer Per-account Time Saved tracking on the dashboard, with week and lifetime totals
Organize larger ministries Team-plan-only campus support with up to 5 campuses and campus-filtered dashboard views
Internal operations Admin Center with customers, support inbox, billing, broadcast messages, and admin-user controls

2.3 Current Entry Paths

  1. Try it Free path: user opens the manual builder without needing an account first; export is free with no payment step.
  2. Account subscription path: user selects Core or Team and moves through signup and Stripe checkout.
  3. Signup-during-checkout path: the signup-checkout edge function pre-creates the account and routes the user back through /signup/complete or /signup-incomplete if email confirmation is still pending.
  4. Authenticated upgrade path: signed-in users can begin subscription checkout from the Account page.
  5. Beta path: approved beta users are flagged on their subscription record and surfaced with a Beta badge on the Account page.

3. Authentication and Account Access

3.1 Core Authentication Model

The application uses Supabase Auth for signup, login, email confirmation, password reset, and session handling. Sessions enforce a 15-minute inactivity lockout. The core public auth routes are:

  • /signup
  • /signup/complete — landing after a successful signup-checkout
  • /signup-incomplete — recovery for an interrupted signup
  • /login
  • /invite-signup
  • /auth/confirm
  • /auth/confirm-email-change — finalizes an admin-initiated email change
  • /forgot-password
  • /reset-password

3.2 Standard Signup Flow

Signup collects user identity, organization information, and a Church Role for the user. If the signup was initiated from pricing, the selected plan price is carried into the signup and checkout path. Pending checkout intent is stored locally so the app can continue into subscription checkout cleanly after email confirmation.

3.3 Email Confirmation and Checkout Continuation

New subscription signups must confirm email through /auth/confirm. After confirmation, the app checks whether there is a pending checkout intent and, if so, routes the user into the subscription checkout path. If the user abandons signup, the abandon-signup edge function and the cleanup-pending-signups scheduled function reconcile the orphaned record.

3.4 Login and Protected Route Behavior

Authenticated users are routed based on both authentication state and subscription state. The platform currently behaves as follows:

Area Requirement Current behavior
Dashboard Authenticated and subscribed Redirects unsubscribed users to /account?requiredSubscription=1
Dashboard creator Authenticated and subscribed Protected under the same rule as the dashboard
Sermon Review Same as creator origin (public or authenticated) Accessible at /create/review/:id or /dashboard/create/review/:id
Account page Authenticated Available even when unsubscribed so billing can be activated or managed
Public creator No account required Supports guest usage; export is free with no payment step
Admin Center Admin user with active status Protected behind AdminProtectedRoute via /admin/login

3.5 Invite-Based Access

The application supports invite-based signup into an existing account.

  • Invite token is validated
  • Invited email is prefilled
  • User joins the existing account structure
  • Team access is then controlled by the account membership model
  • The Account page surfaces pending invites and supports resend

3.6 Email Change (Admin-Initiated)

Customer login emails are not user-editable from the Account page. A support admin can request an email change from the Admin Customer Detail page, which creates a pending email_change_requests row, sends a confirmation link to the new address, and finalizes the swap when the user clicks the link. The confirmation page is /auth/confirm-email-change.

4. Subscription and Billing Execution

4.1 Where Subscription Checkout Starts

Subscription checkout can currently start from:

  • The landing-page pricing section
  • Signup continuation after email confirmation (via create-signup-checkout)
  • The Account page for authenticated users
  • The checkout redirect route at /checkout-redirect

4.2 Subscription Checkout Execution Path

The account subscription flow uses the following execution chain:

  1. User selects a Core or Team price
  2. The app invokes the Supabase Edge Function create-checkout (or create-signup-checkout during signup)
  3. The function validates the selected Stripe price and the user account
  4. Stripe checkout session is created (promotion codes allowed)
  5. Success returns to /dashboard?checkout=success
  6. Cancel returns to the Account page
  7. The stripe-webhook function processes subscription lifecycle and payment events

4.3 Subscription State Refresh

Subscription state is refreshed through the check-subscription Edge Function and the frontend auth context. This refresh matters after:

  • checkout success
  • customer-portal return
  • initial login/session bootstrap
  • any Stripe-webhook-driven status change

4.4 Manage Subscription Modal

On the Account page, subscribed users open a Manage Subscription modal. The current UI presents two actions:

  • Change Subscription on the left
  • Cancel Subscription on the right

Changing a plan opens the plan-management flow and current-plan picker. Cancellation routes through the Account Deletion flow (which is guarded by an exit survey) or the customer-portal cancellation behavior, depending on context.

4.5 Customer Portal Usage

Ongoing subscription management is routed through the customer-portal Edge Function. This is used for plan changes, billing management, and cancellation flows for subscribed users.

4.6 Beta Program

A subscription can carry an is_beta_user flag. Beta users are surfaced with a Beta badge on the Account profile card. A scheduled process-beta-trial-emails function handles beta-period lifecycle messaging.

Operational note: the app assumes Stripe billing-portal settings are correctly configured for the supported prices. Plan changes, renewal visibility, and cancellation behavior depend on that portal configuration being valid in Stripe.

5. Presentation Creation Flow

5.1 Entry Routes

The creator is available in two main forms:

  • /create for public and guest creation
  • /dashboard/create for authenticated subscribed dashboard usage

5.2 Current Form Fields

The sermon creation flow supports the following structured fields:

  • Presentation title
  • Series
  • Presentation date
  • Bible translation
  • Verse breakdown mode
  • Sermon points
  • Verse sections and scripture references
  • Team-plan-only campus selection

5.3 Scripture Lookup Execution

Scripture references are looked up asynchronously while the user types. The frontend calls the Supabase Edge Function scripture-lookup (with esv-lookup for the ESV translation), which resolves scripture content and returns it to the creator flow. Lookup errors are shown inline so the user can correct the reference.

5.4 Content Block Types

Block type User enters Result
Point Sermon point title or content block Generates point-oriented slides
Verse Scripture references Generates scripture slides from lookup results

5.5 Translation and Breakdown Behavior

The creator supports translation-aware scripture lookup and two scripture split modes:

  • Verse by verse
  • Full verses

5.6 Team-Plan Campus Assignment During Creation

Team-plan accounts must assign every presentation to a campus. The campus selector is shown only for Team-plan users and defaults according to the current app state:

  • If the user came from a campus-filtered dashboard, that campus is preselected
  • Otherwise the user preference or primary campus is used
  • Non-Team-plan flows do not show campus selection

5.7 Save and Continue to Sermon Review

When the user submits the creation form, the application saves the sermon record and routes to the Sermon Review step rather than directly to the slide editor.

  • Authenticated account usage saves the presentation to the backend
  • Guest usage stores the presentation locally until later unlock/export steps
  • Series and presentation date are saved as first-class sermon metadata
  • Team-plan presentations also persist campus assignment

6. Sermon Review (Pre-Editor Step)

6.1 Purpose

The Sermon Review page at /create/review/:id (or /dashboard/create/review/:id for authenticated usage) sits between the creator form and the slide editor. It lets the user reorder, re-title, and refine the sermon's points and scripture blocks before slides are generated.

6.2 Capabilities

  • Drag-to-reorder for points and scripture blocks
  • Inline title and content edits
  • Autosave of changes back to the saved presentation
  • Generate Slides action that builds the slide payload and routes to the editor

6.3 Save Lifecycle

Changes on Sermon Review write back to the same saved presentation record that the creator produced, then carry forward into the slide editor. The user can navigate away and return without losing review-stage edits.

7. Slide Editor and Save Lifecycle

7.1 Editor Entry

The slide editor route is /editor/:id. When it opens, the app loads existing editor slides when available. If saved editor slides do not exist yet, it generates a default slide deck from the saved sermon form state.

7.2 Main Editing Capabilities

  • Reorder slides
  • Add or delete slides
  • Edit text
  • Adjust visual styling
  • Apply or upload backgrounds
  • Preview the presentation
  • Print the deck
  • Export when ready

7.3 Autosave and Persistence

The editor autosaves slide changes so users can return later without losing work. For saved account presentations, editor changes persist to the backend. This save lifecycle is part of the recurring dashboard workflow for subscribed users.

7.4 Background Media Handling

Custom backgrounds are handled through the background asset pipeline. The app stores and resolves background assets, and removes obsolete stored backgrounds where appropriate as editor content changes.

7.5 Current Save-State Relationship

The saved presentation model combines:

  • summary metadata for dashboard display
  • structured form data used for generation
  • review-stage block ordering
  • editor slide payload used for final editing and export

8. Export Logic

8.1 Export Decision Logic

Export options open directly for every user, guest or subscribed. There is no payment step and no unlock/checkout gate before export; the previous one-time export checkout (create-guest-checkout / verify-guest-checkout / /payment-success) has been removed along with the large "Preview" watermark that used to gate it. Guests who export without an account are shown an upsell prompt afterward inviting them to create a Core or Team account (SubscriptionUpsellModal) — this is a post-export prompt, not a gate.

Orphaned function note: get-checkout-email still exists in supabase/functions/ and is registered in supabase/config.toml, but has no remaining callers anywhere in the codebase now that the guest-checkout flow it supported has been removed. It has not been deleted as part of this documentation pass; flagging for a future cleanup.

8.2 Export Formats

Format Description Output
PowerPoint (.pptx) Presentation file for PowerPoint-compatible use Widescreen PowerPoint deck download
ProPresenter (.probundle) Presentation bundle for ProPresenter workflows ProPresenter bundle download with presentation data and media support
Print Browser-based print of the deck Opens a print view for paper or PDF output

8.3 Export Validation

Export is validated before file creation. If required data is missing or invalid, export is blocked until the user fixes the issue. The export formatting itself is shared across single export and dashboard bulk export flows.

8.4 Dashboard Bulk Export

The dashboard supports multi-select export. Users select multiple presentations, click Export Selected, choose one format for the full batch, and receive a single zip file containing the selected exports.

9. Dashboard and Ongoing Use

9.1 Dashboard Role

The dashboard at /dashboard is the main operational home for subscribed users. It is where users return each week to create, search, filter, reopen, delete, print, and export presentations.

9.2 Time Saved Card

The dashboard surfaces a Time Saved card that quantifies the value the customer is getting from the platform. It shows:

  • Time saved this week
  • Lifetime total time saved
  • A monthly breakdown the user can step through

9.3 Current Dashboard Controls

The dashboard list supports:

  • Search by title or series
  • Presentation month filter
  • Newest/oldest sorting
  • Refresh button for manual reload
  • Incremental loading with Load More
  • Selection mode for bulk delete and bulk export (visible even with no presentations so onboarding can highlight it during the product tour)

9.4 Presentation Card Behavior

Dashboard cards surface summary metadata rather than just a title.

  • Series label
  • Presentation title
  • Presentation date
  • Slide count
  • Last modified timestamp
  • Campus and former-campus labeling for Team-plan presentations where applicable

9.5 Selection Mode

When users click Select, the dashboard enters a selection mode that supports:

  • Selecting individual presentations
  • Selecting all currently loaded presentations
  • Bulk deleting selected presentations
  • Bulk exporting selected presentations into a zip file

9.6 Campus Filtering for Team Plan

Team-plan users see a campus dropdown on the dashboard. The default option is All Campuses, but the dashboard can also open to a user-selected default campus based on the Account-page preference.

  • All active campuses
  • Archived former-campus labels for presentations moved off deleted campuses
  • Composes with search, month filtering, sort, reload, and pagination

9.7 Product Tour and Replay

A guided product tour walks new users through the dashboard, creator, review, editor, and account stages. After completion or skip, users can replay the tour from the Account page.

9.8 Ongoing Weekly Workflow

  1. User logs in and lands on the dashboard
  2. User reviews the current filtered view of saved presentations
  3. User creates a new presentation or reopens an existing one
  4. User reviews and reorders blocks on Sermon Review
  5. User edits the generated deck and exports or prints
  6. User returns later for the next sermon cycle

10. Account Management and Team-Plan Campuses

10.1 Account Page Structure

The Account page uses expandable accordion-style cards. Major sections stay collapsed until the user opens them. The current sections are:

  • Profile
  • Team
  • Campuses (Team plan only)
  • Subscription
  • Account (includes deletion flow)

10.2 Profile Section

The Profile card contains:

  • Organization
  • Full Name
  • Email (read-only on this page; admin-initiated change is the supported path)
  • Church Role
  • Default Translation
  • Associated Campus (Team plan only) — controls the default campus the dashboard opens to
  • Beta badge if the subscription is flagged as beta

10.3 Team Management

Team operations remain on the Account page and currently support:

  • Viewing team members
  • Viewing roles such as owner and member
  • Viewing each member's Church Role
  • Inviting additional users (subject to plan capacity)
  • Tracking and resending pending invites
  • Owner-only removal of a team member, routed through the remove-team-member edge function

10.4 Team-Plan Campus Model

Team-plan accounts support up to 5 total campuses. A primary Main Campus is ensured for Team-plan accounts and existing Team-plan presentations are backfilled into a campus when needed.

  • Campus management is visible only for the Team plan
  • Only account owners can create, rename, set primary, or delete campuses
  • Team-plan presentations must belong to an active campus
  • Deleting a campus moves its presentations to the primary campus
  • Moved presentations keep the deleted campus name as a former-campus label for filtering

10.5 Subscription Section

The Subscription card shows current status, renewal state, and plan actions.

  • Subscribed users open the Manage Subscription modal
  • Unsubscribed users can activate a plan from the Account page
  • Current plan recognition supports Free, Core, and Team, with monthly or annual billing for Core and Team (Free has no billing)

10.6 Account Deletion

Account deletion is a guarded, multi-step flow:

  1. The user requests deletion from the Account page
  2. The /exit-survey step collects cancellation feedback
  3. A pending deletion record is created and an admin notification is queued
  4. The user can cancel the request before finalization via cancel-account-deletion
  5. The scheduled finalize-account-deletions function performs the eventual hard delete; delete-account handles the cleanup mechanics

10.7 Tour Replay

Users can replay the platform tour from the Account page at any time.

11. Admin Center

11.1 Access Model

The Admin Center is a separate authenticated area behind /admin/login and AdminProtectedRoute. It is reserved for staff with an active record in the admin_users table. Admin invites are sent through the same edge function path and accepted at /admin/accept-invite.

11.2 Layout and Sections

The admin shell exposes these top-level pages:

Route Page Purpose
/admin Overview Active subscription count, recent activity, notification feed, and key metric charts
/admin/customers Customers Search, filter, and export the customer list; click into a customer detail
/admin/customers/:id Customer Detail Account profile, owner contact, Stripe info, presentations, team members, support history, and admin actions including email-change requests
/admin/support Support Inbox of contact-form submissions and cancellation support tickets
/admin/billing Billing Stripe-derived billing visibility and reporting
/admin/messages Messages Broadcast and targeted in-product messages to customers, including beta audience targeting
/admin/users Admin Users Manage internal staff: invite, activate, deactivate

11.3 Admin Capabilities Specific to Customer Detail

  • View Stripe customer and subscription state for the account
  • Export contacts from the customer list
  • Request an email change for the customer owner (sends a confirmation link to the new address)
  • Audit log of admin actions taken against the account
  • Manage support tickets tied to the customer

11.4 Admin API and Audit

All admin operations are routed through the admin-api edge function, which validates the calling admin, performs the requested action with service-role privileges, and writes to admin_audit_logs. Admin notifications surface inside the Overview and persist in admin_notifications.

12. Operational Notes

12.1 Runtime and Platform Dependencies

  • Frontend app is a Vite application deployed via Cloudflare Pages, which auto-builds and deploys from the GitHub `main` branch on every push (no Wrangler CLI involved)
  • Supabase handles Auth, database, storage-related flows, and Edge Functions
  • Stripe handles subscription checkout, promotion codes, and billing portal actions (the previous one-time export payment has been removed)
  • Resend handles transactional email for custom flows (invites, support replies, email-change confirmations)
