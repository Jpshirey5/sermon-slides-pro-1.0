Sermon Slide Pro User Journey Documentation

Prepared from the current implementation in sermon-slides-pro-1.0 as of April 10, 2026. This is the canonical internal operations document in the /docs folder and is intended for support, onboarding, handoff, and product operations.

1. Product Summary

Sermon Slide Pro is a web application for building sermon presentations from a structured sermon form, refining them in a slide editor, and exporting them for presentation software. The application supports both a pay-per-export path and authenticated subscription-based account usage.

Primary user outcome How the platform supports it
Create sermon slides quickly Structured creation flow with title, series, presentation date, points, verses, and automatic scripture lookup
Refine the final deck Slide editor with generation, manual editing, reordering, background control, preview, and autosave
Use slides in service software Export to .pptx and .probundle
Support recurring weekly workflow Saved presentations, dashboard management, account settings, subscription controls, and team support
Organize larger ministries Enterprise-only campus support with up to 5 campuses and campus-filtered dashboard views

2. Website Entry and Conversion Paths

2.1 Public Landing Experience

The public website is the route at / and is composed of the following sections:

  • Hero
  • Features
  • Testimonials
  • Pricing
  • Call to action

Route-level navigation now resets to the top of the page, so when a user returns to the landing page they land back on the hero section instead of their prior scroll position.

2.3 Current Entry Paths

  1. Pay-per-export path: user opens the creator without needing an account first.
  2. Account subscription path: user selects Pro, Team, or Enterprise and moves through signup and Stripe checkout.
  3. Authenticated upgrade path: signed-in users can begin subscription checkout from the Account page.

3. Authentication and Account Access

3.1 Core Authentication Model

The application uses Supabase Auth for signup, login, email confirmation, password reset, and session handling. The core public auth routes are:

  • /signup
  • /login
  • /invite-signup
  • /auth/confirm
  • /forgot-password
  • /reset-password

3.2 Standard Signup Flow

Signup collects the user identity and organization information required to create a full account. If the signup was initiated from pricing, the selected plan price is carried into the signup and checkout path.

New account setup stores pending checkout intent locally so that after email confirmation the app can continue into subscription checkout cleanly.

3.3 Email Confirmation and Checkout Continuation

New subscription signups must confirm email through /auth/confirm. After confirmation, the app checks whether there is a pending checkout intent and, if so, routes the user into the subscription checkout path.

3.4 Login and Protected Route Behavior

Authenticated users are routed based on both authentication state and subscription state. The platform currently behaves as follows:

Area Requirement Current behavior
Dashboard Authenticated and subscribed Redirects unsubscribed users to /account?requiredSubscription=1
Dashboard creator Authenticated and subscribed Protected under the same rule as the dashboard
Account page Authenticated Available even when unsubscribed so billing can be activated or managed
Public creator No account required Supports guest usage and later pay-per-export checkout

3.5 Invite-Based Access

The application supports invite-based signup into an existing account.

  • Invite token is validated
  • Invited email is prefilled
  • User joins the existing account structure
  • Team access is then controlled by the account membership model

4. Subscription and Billing Execution

4.1 Where Subscription Checkout Starts

Subscription checkout can currently start from:

  • The landing-page pricing section
  • Signup continuation after email confirmation
  • The Account page for authenticated users
  • The checkout redirect route at /checkout-redirect

4.2 Subscription Checkout Execution Path

The account subscription flow uses the following execution chain:

  1. User selects a Pro, Team, or Enterprise price
  2. The app invokes the Supabase Edge Function create-checkout
  3. The function validates the selected Stripe price and the user account
  4. Stripe checkout session is created
  5. Success returns to /dashboard?checkout=success
  6. Cancel returns to the Account page

4.3 Subscription State Refresh

Subscription state is refreshed through the check-subscription Edge Function and frontend auth context. This refresh matters after:

  • checkout success
  • customer-portal return
  • initial login/session bootstrap

4.4 Manage Subscription Modal

On the Account page, subscribed users open a Manage Subscription modal. The current UI presents two actions:

  • Change Subscription on the left
  • Cancel Subscription on the right

Changing a plan opens the existing plan-management flow and current-plan picker. Cancellation continues into the current customer-portal cancellation behavior.

4.5 Customer Portal Usage

Ongoing subscription management is routed through the customer-portal Edge Function. This is used for plan changes, billing management, and cancellation flows for subscribed users.

Operational note: the app assumes Stripe billing-portal settings are correctly configured for the supported prices. Plan changes, renewal visibility, and cancellation behavior depend on that portal configuration being valid in Stripe.

5. Presentation Creation Flow

5.1 Entry Routes

The creator is available in two main forms:

  • /create for public and guest creation
  • /dashboard/create for authenticated subscribed dashboard usage

5.2 Current Form Fields

The sermon creation flow now supports the following structured fields:

  • Presentation title
  • Series
  • Presentation date
  • Bible translation
  • Verse breakdown mode
  • Sermon points
  • Verse sections and scripture references
  • Enterprise-only campus selection

5.3 Scripture Lookup Execution

Scripture references are looked up asynchronously while the user types. The frontend calls the Supabase Edge Function scripture-lookup, which resolves scripture content and returns it to the creator flow. Lookup errors are shown inline so the user can correct the reference.

5.4 Content Block Types

Block type User enters Result
Point Sermon point title or content block Generates point-oriented slides
Verse Scripture references Generates scripture slides from lookup results

5.5 Translation and Breakdown Behavior

The creator currently supports translation-aware scripture lookup and two scripture split modes:

  • Verse by verse
  • Full verses

5.6 Enterprise Campus Assignment During Creation

Enterprise accounts must assign every presentation to a campus. The campus selector is shown only for Enterprise users and defaults according to the current app state:

  • If the user came from a campus-filtered dashboard, that campus is preselected
  • Otherwise the user preference or primary campus is used
  • Non-Enterprise flows do not show campus selection

5.7 Save and Continue to the Editor

When the user generates slides, the application saves the presentation state and moves into the editor.

  • Authenticated account usage saves the presentation to the backend
  • Guest usage stores the presentation locally until later unlock/export steps
  • Series and presentation date are saved as first-class sermon metadata
  • Enterprise presentations also persist campus assignment

6. Slide Editor and Save Lifecycle

6.1 Editor Entry

The slide editor route is /editor/:id. When it opens, the app loads existing editor slides when available. If saved editor slides do not exist yet, it generates a default slide deck from the saved sermon form state.

6.2 Main Editing Capabilities

The editor remains the main daily working surface for the product. Users can currently:

  • Reorder slides
  • Add or delete slides
  • Edit text
  • Adjust visual styling
  • Apply or upload backgrounds
  • Preview the presentation
  • Export when ready

6.3 Autosave and Persistence

The editor autosaves slide changes so users can return later without losing work. For saved account presentations, editor changes persist to the backend. This save lifecycle is part of the recurring dashboard workflow for subscribed users.

6.4 Background Media Handling

Custom backgrounds are handled through the background asset pipeline. The app stores and resolves background assets, and removes obsolete stored backgrounds where appropriate as editor content changes.

6.5 Current Save-State Relationship

The saved presentation model now combines:

  • summary metadata for dashboard display
  • structured form data used for generation
  • editor slide payload used for final editing and export

7. Export and Payment Logic

7.1 Export Decision Logic

When a user exports from the editor, the platform applies one of two models:

User state What happens next
Subscribed account user Export options open directly
Guest or non-subscriber without unlock One-time export checkout is required first

7.2 Pay-Per-Export Execution

The pay-per-export path uses the Supabase Edge Function create-guest-checkout. Before redirecting to Stripe, the app stores pending export context locally so that it can restore the presentation after payment.

Success returns to /payment-success, where the app restores the pending presentation and routes the user back into the editor.

7.3 Export Formats

Format Description Output
PowerPoint (.pptx) Presentation file for PowerPoint-compatible use Widescreen PowerPoint deck download
ProPresenter (.probundle) Presentation bundle for ProPresenter workflows ProPresenter bundle download with presentation data and media support

7.4 Export Validation

Export is validated before file creation. If required data is missing or invalid, export is blocked until the user fixes the issue. The export formatting itself is shared across single export and dashboard bulk export flows.

7.5 Dashboard Bulk Export

The dashboard now supports multi-select export. Users select multiple presentations, click Export Selected, choose one format for the full batch, and receive a single zip file containing the selected exports.

8. Dashboard and Ongoing Use

8.1 Dashboard Role

The dashboard at /dashboard is the main operational home for subscribed users. It is where users return each week to create, search, filter, reopen, delete, and export presentations.

8.2 Current Dashboard Controls

The dashboard list now supports:

  • Search by title or series
  • Presentation month filter
  • Newest/oldest sorting
  • Refresh button for manual reload
  • Incremental loading with Load More
  • Selection mode for bulk delete and bulk export

8.3 Presentation Card Behavior

Dashboard cards now surface summary metadata instead of just a title.

  • Series label
  • Presentation title
  • Presentation date
  • Slide count
  • Last modified timestamp
  • Campus and former-campus labeling for Enterprise presentations where applicable

8.4 Selection Mode

When users click Select, the dashboard enters a selection mode that supports:

  • Selecting individual presentations
  • Selecting all currently loaded presentations
  • Bulk deleting selected presentations
  • Bulk exporting selected presentations into a zip file

8.5 Campus Filtering for Enterprise

Enterprise users now see a campus dropdown on the dashboard. The current default option is All Campuses, but the dashboard can also open to a user-selected default campus based on the Account-page preference.

The campus filter supports:

  • All active campuses
  • Archived former-campus labels for presentations moved off deleted campuses
  • Normal composition with search, month filtering, sort, reload, and pagination

8.6 Ongoing Weekly Workflow

  1. User logs in and lands on the dashboard
  2. User reviews the current filtered view of saved presentations
  3. User creates a new presentation or reopens an existing one
  4. User edits and exports the deck
  5. User returns later for the next sermon cycle

9. Account Management and Enterprise Campuses

9.1 Account Page Structure

The Account page now uses expandable accordion-style cards. Major sections stay collapsed until the user opens them. The current sections are:

  • Profile
  • Team
  • Campuses for Enterprise only
  • Subscription
  • Account

9.2 Profile Section

The Profile card now contains:

  • Organization
  • Full Name
  • Email
  • Default Translation
  • Associated Campus for Enterprise accounts

The Associated Campus field controls which campus the dashboard should open to by default. The user can still switch dashboard filters afterward.

9.3 Team Management

Team operations remain on the Account page and currently support:

  • Viewing team members
  • Viewing roles such as owner and member
  • Inviting additional users
  • Tracking and resending pending invites

9.4 Enterprise Campus Model

Enterprise accounts now support up to 5 total campuses. A primary Main Campus is ensured for Enterprise accounts and existing Enterprise presentations are backfilled into a campus when needed.

Current campus rules:

  • Campus management is visible only for Enterprise plans
  • Only account owners can create, rename, set primary, or delete campuses
  • Enterprise presentations must belong to an active campus
  • Deleting a campus moves its presentations to the primary campus
  • Moved presentations keep the deleted campus name as a former-campus label for filtering

9.5 Subscription Section

The Subscription card shows current status, renewal state, and plan actions.

  • Subscribed users open the Manage Subscription modal
  • Unsubscribed users can activate a plan from the Account page
  • Current plan recognition supports Pro, Team, and Enterprise with monthly or annual billing

9.6 Account Deletion

Account deletion remains a guarded flow. The current implementation requires an exit survey before final deletion is completed.

10. Operational Notes

10.1 Runtime and Platform Dependencies

  • Frontend app is deployed as a Vite application with Cloudflare Wrangler
  • Supabase handles Auth, database, storage-related flows, and Edge Functions
  • Stripe handles subscription checkout, one-time export payment, and billing portal actions

10.2 Important Edge Functions in Current Use

Function Current purpose
create-checkout Starts account subscription checkout for the selected price
customer-portal Starts subscription management and plan-change portal flows
check-subscription Refreshes account billing state and plan metadata
create-guest-checkout Starts one-time export checkout for non-subscribed export usage
scripture-lookup Resolves scripture content during the creator flow
send-invite Sends organization invite emails
capture-telemetry Captures app telemetry and error events
delete-account Supports final account-deletion cleanup flow

10.3 Configuration Dependencies to Watch

  • Supabase URL configuration must match the production domain for auth email links
  • Stripe price IDs and billing-portal settings must match the plan catalog used by the app
  • Scripture lookup depends on the scripture function being deployed and correctly configured with its secrets
  • Invite delivery depends on the configured email provider and invite function deployment
  • Enterprise campus behavior depends on the current database migrations being applied
